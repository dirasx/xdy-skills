# Как ведём проект

## Документация и планы

- `README.md` — главная страница проекта. Кратко объясняет, для чего
  нужен проект и что доступно сейчас.
- `WORKFLOW.md` — главный документ о правилах работы. Здесь описано,
  как ведём разработку, проверки и публикацию.
- `PROJECT_STATUS.md` — текущий статус. Здесь видно, что уже
  опубликовано, что сохранено отдельно, что в работе и какой следующий
  шаг.
- `CHANGELOG.md` — история изменений и выпусков.
- `plans/` — планы и согласованные задачи. `plans/next-release.md`
  хранит задачи ближайшего выпуска, а `plans/backlog.md` — «ДЯ · Дальний
  ящик» с отложенными идеями. Задачи из ДЯ берём в работу по отдельному
  решению владельца.
- `docs/` — справочные материалы. Здесь храним согласованные тексты,
  решения по интерфейсу и другие материалы, на которые опирается
  команда.

Если код и внутренние документы хранятся в разных репозиториях,
общий `WORKFLOW.md` лежит в корне закрытого рабочего репозитория.
Статус, бэклог, планы и внутренние решения ведём в папке конкретного
проекта внутри него. Обновляем только документы этого проекта.
Код, общедоступная документация, теги и релизы остаются в
репозитории приложения. Пользовательские данные, реальные выгрузки
и секреты храним вне Git.

Обновляем документы после значимых изменений. Текущий статус ведём в
`PROJECT_STATUS.md`, а подробности оставляем в профильных файлах и
связываем ссылками. Если в старом плане остались открытые галочки,
сверяем их с кодом, статусом и фактом публикации. Когда правила
меняются, поправляем действующие планы, а старые формулировки
явно помечаем как историю.

## Задачи и рабочие изменения

- Задачи получают сквозные ID проекта, например `APP-001`.
  При переносе в план или архив ID сохраняется. Использованные
  номера не выдаём повторно. Старые задачи без номера можно
  оставить как есть по решению владельца.
- Завершённое изменение связываем с ID задачи и коммитом или PR.
  Рабочий номер этапа используем, если такая серия предусмотрена
  действующими правилами проекта. Прежние рабочие номера сохраняем.
- Тип задачи указываем, когда он помогает вести бэклог или дашборд:
  «Баг», «Проверка», «Идея». Тип и приоритет ведём отдельно.

### Приоритет задач

- **Критично** — задача блокирует работу, выпуск или основной
  сценарий приложения.
- **Важно** — задачу стоит взять раньше обычных.
- Без пометки приоритет — «Обычно». Если проект уже ведёт приоритеты
  иначе, сохраняем его формат.

Типы и приоритеты остаются во внутренних документах. В заметках
о выпуске описываем изменения для пользователя.

## Проверки и очередь выпуска

В `CHECKS.md` ведём реестр проверок, от которых зависит готовность
или которые нужно повторять на разных сборках. Используем
существующий формат, например `TEST-025` для задачи `APP-025`,
`TEST-025-1` и `TEST-025-2` для нескольких самостоятельных проверок.
Указываем ID задачи, условия, состояние и, после прогона, дату,
проверенный коммит или сборку и результат. Состояния разработки
и проверки ведём раздельно. Автотест подтверждает только то,
что он реально проверил на указанном коммите или сборке.

В `plans/release-queue.md` собираем завершённые изменения для
выбора состава выпуска. Для каждого указываем ID задачи, краткое
описание, коммит или PR и ссылку на проверку. Явно отмечаем проверки,
которые ещё открыты. Пока обязательная проверка не пройдена,
изменение остаётся в очереди с соответствующей пометкой.

Если в проекте уже есть локальный дашборд, обновляем его по правилам
проекта. Он показывает данные из бэклога, очереди и реестра проверок.
Вносим правки в исходные документы и результаты проверок.

## Подготовка релиза

1. Владелец выбирает состав из очереди и утверждает номер выпуска.
   Используем принятую в проекте схему номера релиза, тега и пакета.
2. Собираем кандидат из согласованных изменений. Фиксируем задачи,
   коммит или сборку, результаты проверок и открытые вопросы.
   Рабочие версии указываем, когда они ведутся в проекте.
3. Готовим заметку для пользователей. Артефакты, язык, порядок
   передачи на публикацию и совместимость обновлений проверяем
   по действующему `WORKFLOW.md` проекта.
4. После подтверждённой публикации записываем дату, версию и коммит
   выпущенных исходников. Добавляем ссылку на заметку или выпуск.
   Отмечаем выпущенные задачи в статусе и выводим их из очереди.
   Историю сохраняем.

## После публикации

- Если проект ведёт архив опубликованных исходников, сохраняем
  очищенный снимок в принятом месте. Фиксируем, какие данные, секреты
  и файлы авторизации исключены.
- Сохраняем заметку там, где ведётся история выпусков проекта.
  Добавляем ссылку на снимок, если он есть.
- Обновляем `PROJECT_STATUS.md` и `CHANGELOG.md`. Если проект ведёт
  отдельный журнал выпусков, записываем в него коммит со снимком
  исходников.
- После подтверждения публикации оформляем тег и GitHub Release, если
  они приняты в проекте. При настроенной автоматизации используем журнал
  выпусков как источник для GitHub Actions.
